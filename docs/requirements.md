## 1. 目的

EvenUpは、身内の立替払いと割り勘を1円単位で記録し、未精算額の確認、個別精算、送金回数を抑えた一括精算を行うモバイルWebアプリである。

全員が同時に精算しない運用を前提とし、元の支払い、実際の送金、送金による充当を別々の事実として保存する。

## 2. 基本方針

1. データ間の紐付けには表示名ではなく一意なIDを使用する。
2. 金額は日本円の整数として扱う。
3. 支払いごとの確定負担額は`payment_shares`を正データとする。
4. 元の支払いを「前回未精算」などの人工的な支払いへ作り替えない。
5. 実際に行った送金を`transfers`へ記録する。
6. 元の負担への充当を`transfer_allocations`へ記録する。
7. 未精算・一部精算・精算済みの状態は保存せず、負担額と有効な充当額から導出する。
8. 精算画面では「個別精算」と「まとめて最適化」の2方式を提供する。
9. 個別精算は一部だけ実施できる。
10. 最適化精算は表示された全ルートを一括で実施する場合だけ利用できる。
11. 支払い、送金、送金バッチは物理削除せず、取消履歴を残す。

## 3. システム構成

| 区分 | 採用技術 | 役割 |
| --- | --- | --- |
| フロントエンド | GitHub Pages / HTML / CSS / JavaScript | 画面、入力、API通信 |
| バックエンド | Google Apps Script Webアプリ | 認証、検証、計算、データ操作 |
| データストア | Googleスプレッドシート | メンバー、支払い、負担、送金、充当 |
| 端末内保存 | `localStorage` | グループ別の共有アクセスキー、操作ユーザ、精算表示モード、直前支払者（旧設定互換） |
| 通信 | Fetch API / HTTPS / JSON | フロントエンドとGAS間 |

GAS Webアプリはスクリプト所有者の権限で実行する。

## 4. 対象ユーザーと前提

- 特定の身内グループで利用する。
- コードは全グループで共有し、URL、GAS、スプレッドシート、アクセスキーはグループごとに分離する。
- 主な利用端末はスマートフォンとする。
- 日本円のみを扱う。
- 基準タイムゾーンは`Asia/Tokyo`とする。
- 個人アカウントと権限ロールはMVPでは設けない。
- メンバー管理はスプレッドシートを直接編集して行う。
- 全員の残高が同時に0円にならない継続運用を許容する。

## 5. 認証

- グループ共通の256ビット相当のランダムなアクセスキーを使用する。
- 初回認証成功後、キーを`group_id`で名前空間化した`localStorage`へ期限なしで保存する。
- 設定画面でこの端末の操作ユーザを選択し、`localStorage`へ期限なしで保存できる。
- 起動時と各API呼び出し時にGASで検証する。
- 無効な場合は端末内のキーを削除して入力画面へ戻す。
- 設定画面からこの端末をログアウトできる。
- 生のキーをGitHub、スプレッドシート、ログへ保存しない。
- GASのScript PropertiesにはSHA-256ハッシュだけを保存する。
- 外部広告、解析、出所不明のJavaScriptを導入しない。

## 6. 画面

### 6.1 アクセスキー入力

- 保存済みの有効なキーがない場合に表示する。
- キーの入力、認証、エラー表示を行う。

### 6.2 記録

- 内容、金額、支払者、対象メンバーを入力する。
- 有効メンバーだけを選択肢へ表示する。
- 登録中はボタンを無効化する。
- 通信失敗時は同じ`request_id`で再送できる。

### 6.3 精算

画面上部で次の表示方式を切り替える。

#### 個別精算

- 元の支払いから生じた未精算債務を、債務者から元の支払者への直接送金として表示する。
- 同じ債務者・受取者の残債は合算表示する。
- 内訳として元の支払いと残額を表示する。
- 任意の1組だけ精算できる。
- 提案額以下の一部金額を送金として記録できる。
- 充当は古い債務から順に行う。

#### まとめて最適化

- 全残債を純収支へ変換し、送金回数を抑えたルートを表示する。
- 本来直接の貸し借りがない相手への送金を含む場合がある。
- 表示されたルートの一部だけを実施することはできない。
- 全ルートを実際に送金したことを確認して一括記録する。
- 送金0件で全残債が相殺される場合も、一括精算として記録できる。

共通表示:

- メンバー別純収支
- 未精算または一部精算の支払い一覧
- 最新の有効な送金バッチの取消

### 6.4 履歴

- タブを開くまで取得しない。
- 初回20件、以後20件ずつ取得する。
- 「すべて」「支払い」「送金」の表示切替を提供する。
- 支払いには`未精算`、`一部精算`、`精算済み`、`取消済み`を表示する。
- 送金には`個別精算`、`最適化精算`、`取消済み`を表示する。

### 6.5 設定

- 最新状態の再取得
- この端末からログアウト

## 7. 支払い

### 7.1 登録

| 項目 | 条件 |
| --- | --- |
| 内容 | 1〜100文字 |
| 金額 | 1〜99,999,999円の整数 |
| 支払者 | 有効メンバー |
| 対象者 | 有効メンバー1人以上、重複不可 |

サーバーが`payment_id`、日時、各負担額を確定する。

### 7.2 端数

対象人数を`n`、金額を`amount`とする。

1. 全員へ`floor(amount / n)`円を割り当てる。
2. 余りを1円ずつ配る。
3. 支払者が対象に含まれる場合、支払者以外へ先に配る。
4. 候補内では`member_id`昇順とする。

例: 支払者M001、対象M001・M002・M003、1,000円

| メンバー | 負担額 |
| --- | ---: |
| M001 | 333円 |
| M002 | 334円 |
| M003 | 333円 |

### 7.3 債務

- 対象者が支払者本人の場合、その負担額は送金不要であり、債務を生成しない。
- 対象者が支払者以外の場合、対象者から支払者への債務を生成する。
- 元債務額は`payment_shares.share_amount`とする。
- 残債は元債務額から有効な`transfer_allocations`の合計を引いて求める。

### 7.4 状態導出

支払者本人の負担額を除いた合計を`settleable_amount`、有効充当合計を`allocated_amount`とする。

| 条件 | 状態 |
| --- | --- |
| `payments.cancelled_at`あり | `CANCELLED` |
| `settleable_amount = 0` | `SETTLED` |
| `allocated_amount = 0` | `UNSETTLED` |
| `0 < allocated_amount < settleable_amount` | `PARTIALLY_SETTLED` |
| `allocated_amount = settleable_amount` | `SETTLED` |

### 7.5 編集・取消

- 取消されておらず、有効な充当が1円もない支払いだけ編集・取消できる。
- 一部でも精算済みの場合、関連する送金バッチを取り消して充当を0円へ戻してから編集・取消する。
- 編集時は`payment_shares`を再計算して置換する。
- 更新時は`updated_at`による楽観ロックを行う。
- 取消時も支払いと負担行を物理削除しない。

## 8. 個別精算

### 8.1 表示計算

残債を次のキーで集約する。

```text
2人のmember_idを並べたペア
```

同じ2人の間でA→BとB→Aの残債が両方ある場合は相殺し、個別精算候補には差額だけを実送金額として表示する。
各グループに元の支払い内訳を付け、古い`paid_at`順、同時刻なら`payment_id`順に並べる。
差額が0円の場合は「送金なしの相殺」候補として表示する。

### 8.2 送金登録

- 送金元、送金先は2人間で相殺後に差額を払う向きで固定する。
- 金額は、差額がある場合は1円以上・候補差額以下、差額0円の相殺のみの場合は0円とする。
- 逆方向の残債がある場合は、逆方向分を相殺として同じバッチで充当する。
- 実送金額と相殺額を合算した額を、差額支払い側の残債へFIFOで充当する。
- 1回の個別精算を1つの`transfer_batch`として保存する。
- バッチ内の実送金は1件とする。
- 充当結果を`transfer_allocations`へ保存する。

例:

```text
シャ卿 → ナカチ 1,334円
  ラーメン 334円
  レンタカー 1,000円
```

1,000円を送金した場合:

```text
ラーメンへ334円充当
レンタカーへ666円充当
レンタカーの残債334円
```

新しい「前回未精算」支払いは作成しない。

## 9. 最適化精算

### 9.1 純収支

すべての残債について:

- 債権者へ残債額を加算する。
- 債務者から残債額を減算する。

残高合計は必ず0円でなければならない。

### 9.2 ルート

決定的な貪欲法を使用する。

1. 債権者を受取額降順、同額時`member_id`昇順で並べる。
2. 債務者を支払額降順、同額時`member_id`昇順で並べる。
3. 先頭同士で小さい残額を送金額とする。
4. 残額0円のメンバーを除外し、全残高が0円になるまで続ける。

数学的な最小送金回数を常に保証するものではない。

### 9.3 一括記録

- 表示中の全ルートを1つの`OPTIMIZED`送金バッチとして記録する。
- 一部ルートだけの記録は禁止する。
- バッチ作成時点の全残債を`transfer_allocations`へ全額充当する。
- 実送金ルートと元債務の対応は、同じバッチを介して保持する。
- 送金ルートが0件でも残債が相互相殺される場合は記録可能とする。
- スナップショットが変わっていた場合は記録せず再確認を求める。

## 10. 送金取消

- 取消可能なのは、`transferred_at`が最も新しい有効な送金バッチだけとする。
- 同時刻の場合はシート行番号が大きいものを最新とする。
- 取消時は送金バッチを`CANCELLED`にする。
- 配下の送金と充当は削除せず、バッチが取消済みのため計算から除外する。
- 取消後、支払い状態と残債を再計算する。
- 古いバッチを取り消す場合は、新しい有効バッチから順に取り消す。

## 11. 初期読み込みと性能

初期起動で取得するもの:

- メンバー
- 残債がある支払いと負担内訳
- 個別精算候補
- 最適化精算候補
- メンバー別純収支
- 最新の取消可能な送金バッチ

履歴全件は取得しない。

MVPでは各シートを必要範囲ごとに一括取得してGAS上で計算する。未精算専用シートとキャッシュは初期実装では使用しない。

## 12. 同時実行・二重登録

- 操作中はフロントのボタンを無効化する。
- 支払い作成と送金バッチ作成にはクライアント生成UUIDの`request_id`を付与する。
- 同じ`request_id`では既存結果を返す。
- 支払い作成・編集・取消、送金作成・取消はScriptLock内で処理する。
- ロック内でデータを再取得し、残債と操作条件を再検証する。
- 個別精算は対象グループと残債を再検証する。
- 最適化精算はスナップショットトークンを再検証する。

## 13. データ整合性

- 負担額合計は支払総額と一致する。
- 有効充当合計は元債務額を超えない。
- 個別精算の充当先は送金元から送金先への直接債務に限る。
- 個別バッチの送金額と充当合計は一致する。
- 最適化バッチの作成時残債は全額充当される。
- 最適化バッチの全送金によるメンバー別増減は、充当した全残債の純収支と一致する。
- 複数シート更新はロック内で事前検証、退避、書込、事後検証を行う。
- 途中失敗時は退避値へ復元する。

## 14. 非機能要件

- スマートフォン片手操作を優先する。
- タップ領域は最低44×44pxとする。
- 金額は3桁区切りで表示する。
- 色だけに依存せず状態をテキストで示す。
- すべての通信をHTTPSで行う。
- サーバー側ですべての入力を再検証する。
- 生のアクセスキーと内部エラー詳細をログ・レスポンスへ出さない。
- GASのコールドスタートや無料枠により一定応答時間は保証しない。

## 15. MVP対象外

- 個人アカウント、権限ロール
- 複数グループ、複数通貨
- レシート画像
- 外部決済連携
- オフライン登録
- メンバー管理画面
- 最適化ルートの一部実行
- 厳密な最小送金回数
- 任意の古い送金バッチの直接取消

## 16. 受入条件

1. 1,000円を3人で割り、支払者333円、他の1人334円、もう1人333円になる。
2. 元の支払いを変更せず、一部送金後の残債を表示できる。
3. 個別精算で任意の債務者・受取者の組だけを精算できる。
4. 個別精算で提案額未満を送金し、FIFOで複数支払いへ充当できる。
5. 支払い状態が未精算から一部精算、精算済みへ自動変化する。
6. 最適化精算は全ルート一括でのみ記録できる。
7. 最適化精算後、対象だった全残債が0円になる。
8. 最新の有効な送金バッチだけを取り消せる。
9. 送金取消後、充当が無効になり残債と状態が復元される。
10. 有効な充当がある支払いは編集・取消できない。
11. 同じ`request_id`の再送で支払い・送金が重複しない。
12. 履歴を20件ずつ取得できる。
13. 無効なアクセスキーで業務データを取得できない。
